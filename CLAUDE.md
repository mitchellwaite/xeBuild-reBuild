# CLAUDE.md

Matching rebuild of `xeBuild.exe`; see README.md for findings, layout and the pipeline.

## Rules

- `xeBuild.exe` in the repo root is the reference. Never modify it; analyse copies
  (IDA writes `.i64` next to its input, so point IDA at a copy under `build/`).
- Success is measured by bytes: `sh build.sh` must end with SHA256
  `10dac648197fa5cdbb82d975ab9ff11f64075c9686908dfd9a33edc533f1971c` (it also
  runs `re/execmp.py`, which names any differing header field or byte).
- `src/**/*.s` and `src/objects.txt` are generated by `re/split.py` from
  `build/xeBuild.lines.json` (`re/ddfix.py`). Change them by changing those
  scripts and regenerating; regenerating overwrites hand edits to `.s` files.
- `src/**/*.c` are hand-maintained (XeCrypt's sources, see README). An
  object with a `.c` gets no `.s` from `split.py`; `build.sh` compiles it with
  the per-directory flags and original `__FILE__` path set there. When moving
  an object to C, put names for the functions it shares with `.s` files in
  `split.py`'s `SYMBOLS` and regenerate. Keep third-party licence notices intact.
- Move big objects to C one function at a time (mixed objects, README): add
  the function's address to `split.py`'s `C_FUNCS` and its name to `SYMBOLS`,
  write it in `src/<obj>.c`, regenerate. Leave hard functions in asm and come
  back to them later. C functions in a mixed object can't emit data (string
  literals, switch tables); use `extern` names for the `.s`'s data.
- Keep README's Progress section current: after converting an object or
  function (or parking one in `wip/`), run `sh build.sh` then
  `python re/progress.py`, and commit the README with the change. The section
  is generated; change `re/progress.py` (e.g. its `NOTES` for wip drafts),
  not the README text between the `progress:begin/end` markers. Update the
  "Move functions to C" row in Status by hand when the totals move.
- To match a function before a full build: `python re/fncmp.py src/<obj>.c
  <name> [flags]` (MATCH or a diff against the original). For a whole C
  file, compare its `.text` against `build/obj/<obj>.o` from the asm build
  (objdump without addresses). Then run the full build.
- File names and boundaries live in `re/split.py` (`NAMES`, with the evidence
  for each). Data boundaries are inferred; keep 4-byte alignment of every
  section piece (gas pads sections to 4).
- Commit without asking whenever a milestone is verified: a coherent step
  (for example a component moved to C, or a pipeline change) is finished and
  `sh build.sh` reproduces the SHA256. Don't commit a build that doesn't match.
  Push to `origin` after each commit.
- Never force push (`--force`, `--force-with-lease`, `+refspec`) or rewrite
  pushed history. If a push is rejected, something went wrong: stop and ask.
- Don't hand-patch the linked exe beyond `re/stamp.py` (timestamp + checksum);
  every other difference must be fixed in the source, linker script or ddfix.
- Only use the pinned toolchain in `tools/toolchain-4745/` (gcc 6.2.0, binutils
  2.27, crt 4745). Newer binutils encode differently. gcc needs its `bin/` on
  PATH (cc1 and as load DLLs from there); otherwise it fails silently.

## Environment gotchas (Windows 11)

- Bash tool is Git Bash. When calling `wsl` with paths, export
  `MSYS_NO_PATHCONV=1`, and put multi-line WSL work in a script file rather
  than `bash -c "..."` (quoting breaks).
- WSL is Ubuntu 26.04 running as **WSL1** with no passwordless sudo.
  `dpkg-deb -x` fails there ("Function not implemented"); `install.sh` unpacks
  with Python instead. ddisasm lives in `~/ddisasm-root`; source
  `tools/ddisasm/env.sh` before using it.
- Pass absolute paths to executables from Python `subprocess` on Windows.
- Write generated text with `newline='\n'`; `.gitattributes` enforces LF
  (the `.sh` files must be LF for WSL bash).
- Never `rm -rf` a directory from a variable or glob (a safety check blocks it);
  write to a fresh directory or let the generator overwrite in place.
- In Python edit scripts, string escapes like `'\n'` / `'\0'` get mangled through
  heredocs; use the Edit tool for code changes.
- IDA 9.4 idalib: `python script.py` with the pip-installed `idapro` wheel; don't
  use `python -I` (hides the user site-packages where it lives).
